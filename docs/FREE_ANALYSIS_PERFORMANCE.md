# 自由分析性能排查（2026-10-02）

## 定位到的问题

- 开局树保存会因为评分变化而清空节点、布局缓存。节点重建在主线程逐步验证走法、生成 SAN。实际数据副本中，794 节点的一次冷重建约 415 ms；这段工作可以直接阻塞交互，并非等待引擎结果。
- macOS UCI 搜索没有响应 Swift 任务取消。切换局面后旧搜索仍算到目标深度，新请求等待旧搜索释放。
- 同一局面的重复候选请求会取消、重建任务；自由分析没有使用开局树中已有的同引擎棋步评分。
- 棋步评分的棋谱回放、SAN 与解释整理原本运行在主线程。

## 修改

- 保留稳定路线前缀对应的局面与 SAN，新增路线只计算未知步骤；节点关系、来源计数仍按最新文档生成。隐藏、删除、恢复、深度限制继续独立生效。
- 只有评分变化时更新节点标记，保留布局；评分移除同样立即反映。
- macOS 取消搜索时发送 UCI stop，并消费该搜索的 bestmove 后才启动下一请求。每次搜索使用独立标识，避免迟到的取消中断下一局面。
- 相同正在分析的请求合并，120 ms 内连续切换只搜索最后局面；已有候选缓存直接恢复。
- 自由分析复用同版本、同引擎、至少深度 14 的开局树评分。未知走法继续正常评价。
- 棋谱回放、棋步评价的纯计算移出主线程，保持原分析深度和质量判定。

## 验证

- 51 项自动测试通过；新增覆盖连续换局面、重复请求、UCI 取消及后续输出隔离、路线缓存更新和隐藏恢复，补充已有测试验证评分缓存删除/恢复与自由分析复用。
- macOS、iOS 通用设备构建通过。
- 实际 Stockfish 18：深度 30、三个候选搜索开始后取消，释放耗时约 0.35 ms；下一局面正常返回深度 14、三个候选（该样本引擎耗时 131 ms）。这是单次样本，不是延迟上限。
- 本地数据副本中，一棵 315 节点树冷生成约 208 ms；缓存预热后，追加来源并保存、刷新共约 40 ms；评分删除并保存、刷新约 30 ms。测量包含同步写盘，属于组件耗时，不是整帧耗时。794 节点的首次基线与后续样本不作直接百分比比较。

首次加载树仍需构建缓存，原子保存仍同步写盘；复杂局面的深度搜索也可能需要更久。此次解决的是已确认的重复重建与搜索排队，没有降低分析深度，也不保证所有设备或局面完全无延迟。iOS 通过构建检查，未在真机测量；UCI 立即取消改动仅适用于 macOS 进程引擎。
